# GitHub Pages: eliminate competing publishers and distinguish site version from forecast vintage

**Incident observed:** 11 November 2026, following owner merge of PR #164.

## What happened

The owner provided a one-page Safari PDF of the election dashboard showing a forecast dated 31 October. Its embedded PDF metadata gives a creation time of **10 November 2026 15:11:16 UTC**, which is **11 November, 02:11:16 AEDT**. The PR #163 Next.js deployment completed **at 02:11:49 AEDT**, 33 seconds later. That PDF therefore records the previous website build, regardless of browser caching.

A later PR #164 push revealed **two separate Pages publishers triggered by the same main commit** `6f7e87de314ce0709a8b6a05807eee09bab85d3d`:

| Workflow | Run | Actual publication source | Result |
| --- | --- | --- | --- |
| [Deploy website to GitHub Pages](https://github.com/MusicOfScience/vic-election-2026/actions/runs/42846284489) | #42846284489 | **Custom Next.js** static build in `./out` | Success 02:41:17 AEDT |
| [pages build and deployment](https://github.com/MusicOfScience/vic-election-2026/actions/runs/42846283191) | #42846283191 | **GitHub-managed Jekyll**: log says `Source: /github/workspace/./docs` | Success 02:41:39 AEDT |

The Jekyll deployment finished **22 seconds after** the intended dashboard deployment and therefore **can replace the site's static content with a build of `/docs`**. A green custom workflow is not adequate proof that the dashboard remains served by GitHub Pages. The web crawler could not fetch the live user-hosted CDN during this incident, so this is confirmed *conflicting publisher configuration and deployment chronology*, not an independently fetched live-site byte comparison.

**Root cause requiring a repository-admin UI change:** GitHub Pages is configured to deploy from a branch/`/docs` while the project also runs its own custom Next.js Pages action. GitHub documentation says an app with a custom build should configure **Settings → Pages → Build and deployment → Source → GitHub Actions**.

## Required owner action (do this before merging the fix PR)

1. Visit <https://github.com/MusicOfScience/vic-election-2026/settings/pages>.
2. Under **Build and deployment → Source**, select **GitHub Actions** (not **Deploy from a branch** with `main /docs`). The custom `.github/workflows/deploy-pages.yml` already exists; do not add GitHub's generic suggested starter template.
3. Save, then merge the fix PR to launch a new, single-source Next.js build. Check that its **build and deploy jobs are both successful**.
4. Check the app on an iPhone: the heading should show **Forecast snapshot 31 October** and a newer **Website compiled** timestamp and short SHA, visible beside one another. Refresh/reopen the site if a cached copy persists.
5. The recurring **pages build and deployment** native Jekyll run should no longer be generated by subsequent pushes. If it is still generated, inspect Pages settings and environment before declaring the publishing race fixed.

## New fail-closed guard

`deploy-pages.yml` now calls `gh api repos/$GITHUB_REPOSITORY/pages --jq .build_type` before the expensive build and **fails with a specific actionable message** unless `build_type == "workflow"`. Existing job `permissions.pages: write` permits the repository Pages read. This prevents more deceptive green custom builds while a parallel `/docs` publisher remains enabled. The repository admin must still select GitHub Actions as the publishing source in the UI; the code does **not** silently change repository settings.

The public site also includes build metadata `NEXT_PUBLIC_SITE_BUILD_DATE` and `NEXT_PUBLIC_SITE_BUILD_SHA` compiled during the custom Pages build. It displays the date/short SHA adjacent to the independent canonical forecast date.

## Forecast and source freshness are a separate issue

The **31 October 2026** experimental model and its 5,000 simulations remain unchanged because no newer survey has completed governed admission. The new November DemosAU/Resolve/Lighthouse/Pakenham sources are reviewed but **held**; the header now shows the 11 November assessment, unlike the old October-only campaign status.

The public readiness indicator legitimately fell from **6/9 (31 Oct)** to **5/9 (11 Nov)** because VEC enrolment data were last effective **4 September**. Under the `metadata/sources.json` `vec-2026-enrolment` 62-day threshold, the data are 68 days old on 11 November. The VEC now indexes **October district and region enrolment spreadsheets** (<https://www.vec.vic.gov.au/enrolment/electoral-roll-statistics>), which require source-byte verification and owner-reviewed data admission before any freshness threshold or model files can change. See [issue #167](https://github.com/MusicOfScience/vic-election-2026/issues/167). Do not simply change the effective date to reopen the gate.

**Non-changes:** no forecast input, simulated result, model code, historical validation result, candidate admission, preference scenario, prospective election registration, or production authorisation changes in this publishing-clarity fix.
